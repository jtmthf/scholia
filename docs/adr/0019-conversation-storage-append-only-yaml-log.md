# A Conversation is one append-only YAML stream on disk

## Status

accepted

> **Update (2026-08-05, issue #33):** union merge turned out not to be safe with a bare
> `---` separator, and the format now carries **id-tagged document markers** — `--- # <id>`
> to open and `... # <id>` to close. See the last consequence below; the decision is
> unchanged, its bytes are.

## Context & Decision

The Sidecar (ADR-0018) can be committed to git, which makes **merge behaviour a data-model
constraint**, not an implementation detail. A format that conflicts badly is a format
people delete.

**One file per Conversation**, named by a **UUIDv7**, as a **multi-document YAML stream**
that is only ever appended to. Document 0 is the conversation header (id, page path, the
original Anchor, author, timestamp), written once at creation and never modified.
Documents 1..n are **events** — `comment`, `edited`, `deleted`, `reacted`, `resolved`,
`reopened`, `reanchored`. Current state is a fold over the stream at read time, with
last-write-wins keyed on event id.

Threads and Chats live in separate directories, so **visibility is enforced by the
filesystem** rather than by a field: the private directory carries its own ignore file and
no `git add` can sweep it up by accident.

`.gitattributes` marks the store `merge=union`, so git resolves concurrent appends by
keeping both sides instead of raising a conflict.

The design is chosen so that **nothing is ever mutated**:

- Different Conversations are different files with unguessable names, so concurrent
  creation merges cleanly with no special handling.
- Concurrent replies to the _same_ Conversation are appends, which `merge=union` keeps
  both of — semantically correct for a comment log, with ordering recovered from
  timestamps rather than file position.
- Because the header is immutable and every state change is an event, union merge can
  never corrupt a field. This is the property that makes union merge _correct_ rather than
  a patch over a hazard.

The **aggregate boundary, the storage atomicity unit, and git's merge unit all coincide**
at the Conversation. That is why this shape was chosen over anything finer or coarser.

## Considered Options

- **One file per Site, or per Page.** Rejected: per-Site collides on every write; per-Page
  collides on every same-page comment.
- **One file per Comment.** Better conflict profile still — nearly every write is a new
  file. Rejected because the file is the agent-facing artifact: one Conversation per file
  means an agent reads a whole thread, anchor and resolve state included, in a single
  read, with no join. Union merge buys back most of the conflict risk that costs.
- **Markdown with an HTML-comment sentinel** (`<!-- scholia:comment id=… -->`). Attractive
  because it renders as a readable thread. Rejected: it requires escaping discipline
  forever, and a comment body containing the sentinel corrupts the conversation
  permanently — in a tool whose users write about markdown for a living. YAML block
  scalars are delimited by indentation and never parsed, so no body can escape its own
  field. The rendering advantage was also mostly illusory: teammates meet these files in
  PR _diffs_, which GitHub does not render as markdown either.
- **TOML.** Rejected: multi-line strings are `"""`/`'''`-delimited, reintroducing exactly
  the delimiter fragility we are escaping.
- **A single YAML document with a top-level sequence.** Works, but only by convention — it
  _looks_ like a mutable list, and the first reformat breaks the append-only invariant. A
  stream has no closing token, so appending is always structurally valid.
- **ULID instead of UUIDv7.** Both are unique-without-coordination and time-sortable.
  UUIDv7 wins because `packages/db/src/schema.ts` already declares every id as a Postgres
  `uuid` column, so one id scheme spans local files and hosted rows with no migration.

## Consequences

- **Ids move from the database to the application.** The schema currently uses
  `.defaultRandom()` — v4, generated by Postgres. The Sidecar has no database to default
  from and the application cannot have two identity stories, so aggregates assign their own
  UUIDv7. Node has no built-in v7 generator, so this costs one small dependency.
- **The fold must dedupe by event id.** Union merge takes lines from both sides; a
  cherry-pick or rebase could deliver the same event twice. Deduping makes that a no-op
  instead of a double-post.
- **Ids must be quoted and bodies written as explicit `|` block scalars**, or YAML's
  implicit typing will mangle them.
- **A `.yaml` file does not render as a thread on GitHub.** The human-readable path is
  Scholia rendering its own conversation files, or a CLI printer — not the raw file.
- Comment _edits_ and deletes are events, not rewrites, so "append-only" is a real
  invariant rather than a convention — but it is one the writer must enforce.
- **Every document must be delimited by a line unique to it**, which a bare `---`
  separator is not. Before `merge=union` keeps both sides of a conflicting region, git
  trims the leading and trailing lines the two sides have in common — so two concurrent
  appends, each opening with `---`, have that line emitted once and their two documents
  spliced into one, where the later keys win and an event is lost outright. Two events
  identical but for their ids (concurrent `resolved`s, say) lose their trailing lines the
  same way. No fold can recover from either, because the damage is done before the parser
  sees the file. The format therefore writes `--- # <id>` to open a document and YAML's
  explicit document-end marker `... # <id>` to close it, so no two blocks share a first or
  last line and there is nothing for git to trim. This is what actually makes union merge
  correct; the immutable header is necessary but was not sufficient. Streams written
  before this still parse — the markers are the writer's contract, not the reader's.
